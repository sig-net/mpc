# Findings: consensus-checkpoint freeze — root cause verified, fix designed

> Root-cause analysis and fix design for the consensus-checkpoint freeze, July 2026. Code references are relative to `chain-signatures/` as of `fix/canton-respond-idempotency`; production evidence comes from GCP log exports of the `near-cs-dev` dev cluster (reproduction queries in §7b). Shareable summary: `consensus-freeze-proof.md`.

## Verdict

- **H1 (digest divergence): CONFIRMED — and as of 2026-07-16, production-proven (§7): 58/58 cross-node heights divergent, id-sets identical on Ethereum while every digest differs; consensus frozen ≥30 days on both chains; zero checkpoint publishes in 14 days.** The mechanism is more complete than hypothesized. The consensus vote *is* the threshold-MPC signature over the digest, and a node can only co-sign a checkpoint whose digest it computed byte-identically itself. Any divergence ⇒ no cohort ⇒ nothing ever signed ⇒ the NEAR value never advances. Divergence is not occasional — it is structural and, once requests get stuck, permanent.
- **H2 (governance/NEAR stall): REFUTED as primary cause.** The NEAR *read* path is provably healthy (the 986 Canton + 91 Ethereum "confirmed and persisted" lines each require a successful poll of the contract, `node/src/rpc/mod.rs:400-466`, every 10s). The *write* path (`respond_checkpoint`) is unreachable by construction while digests diverge — signing never completes, so there is nothing to publish. One residual production check remains (see §7).
- **H3 (stuck requests): EXPLAINED.** Canton's 18–19 stuck entries are bidirectional deposits whose on-ledger sign-event contracts are already consumed and whose EVM execution the node never observes — with no TTL they are permanent residents, and the requeue→re-sign→re-publish churn after every restart keeps their bytes diverging across nodes forever.
- **Two additional systemic defects found (not in the dossier):**
  1. **Cap-full pipeline livelock.** When 32 unconfirmed checkpoints accumulate (`MAX_PENDING_CHECKPOINTS`, `node/src/backlog/mod.rs:19`), `has_checkpoint_slot` gates off *both* `process_next_block` and catchup item processing (`node/src/stream/pipeline.rs:237,297`) — the chain's entire event indexing stalls on that node. Confirmation at the frozen height evicts nothing (`retain(height > 533730)`, `mod.rs:618`), and watchdog restarts never clear the pending map (only `recover_by_checkpoint` or a pod restart does). Ethereum, with a 20-block interval on a ~3 blocks/s chain, refills the cap ~4 minutes after every pod start and then stops indexing except for futile ~35-minute watchdog cycles.
  2. **Zombie checkpoint sign tasks.** Checkpoint sign requests are tagged `chain: NEAR` (`primitives/src/requests.rs:108`), so `SignCommand::AbortChain(<chain>)` never reaps them (`task_chains` filter, `node/src/protocol/request/mod.rs:115,327-336`), nothing ever sends `Completion` for them, and a diverged task loops organize→posit→reorganize forever. Up to 32 zombies per chain compete for the 4 proposer slots (`MAX_CONCURRENT_PROPOSERS`, `mod.rs:52`), degrading real signing latency until pod restart.

## 1. The verified causal chain

1. **Checkpoint creation.** Every `interval` blocks, `process_block_event` (`node/src/stream/ops.rs:371-406`) snapshots the chain's backlog: each pending entry is CBOR-serialized **whole** — `BacklogEntry { request: IndexedSignRequest, status: SignStatus }` — into `PendingTx.transaction` (`node/src/backlog/mod.rs:106-127`), sorted by sign_id.
2. **The digest hashes those raw bytes.** `Checkpoint::digest()` (`primitives/src/backlog.rs:65-74`) = SHA3(caip2 ‖ height ‖ ∀entry: request_id ‖ CBOR-bytes). A unit test (`node/src/backlog/mod.rs:1390-1429`, `test_checkpoint_digest_changes_with_status`) even *asserts* the digest changes with status — the divergence is designed-in, presumably from an incomplete refactor: the canonical `SignStatus::digest_bytes()` (`node/src/sign_bidirectional.rs:54-67`) is dead code, never called anywhere.
3. **Consensus = threshold-signing that digest.** The checkpoint becomes a sign request whose `sign_id = SHA3("checkpoint" ‖ caip2 ‖ height ‖ sign_payload_hash ‖ key_version)` (`primitives/src/crypto.rs:87-96`) — a pure function of the digest. Proposer election is seeded by `entropy = sign_id` (`node/src/protocol/request/organize.rs:11-19`), so all nodes holding the *same* digest deterministically cooperate.
4. **A node can only co-sign its own digest.** Sign tasks spawn exclusively from the node's own `SignCommand` (`node/src/protocol/request/mod.rs:301-320`); a peer's `Propose` for an unknown sign_id lands in an orphan posit inbox that no task ever subscribes to (`mod.rs:195-228`). So a checkpoint reaches threshold participation **iff ≥ threshold nodes computed byte-identical digests at that height**.
5. **The bytes are structurally node-local.** Divergence sources inside `pending.transaction`, in decreasing severity:
   - `unix_timestamp_indexed` — **local wall clock at event-parse time** on both Canton (`chain-canton/src/events.rs:15-19` → `:62`) and Ethereum (`chain-ethereum/src/event_parsing.rs:150`, `chain-ethereum/src/util.rs:4`). ±1s races on live indexing; hours apart after replay (below). The "preserved across recoveries" doc comment (`primitives/src/requests.rs:31-33`) only holds for checkpoint-restored entries, and only until replay clobbers them.
   - `status: SignStatus` — phases advance on async triggers (signing-cohort completion via `mark_publishing`, target-chain execution observations via `process_execution_confirmed`), never synchronized to source-chain block boundaries. Non-cohort nodes stay `PendingGeneration` while cohort members hold `PendingPublish`.
   - `PublishState { signature, participants, is_proposer }` (`node/src/sign_bidirectional.rs:14-18`) — written into the backlog on every generation success for non-checkpoint requests (`node/src/protocol/signature.rs:259-280`). `is_proposer` is true on exactly one node **by definition**; `signature`/`participants` differ per re-signing cohort.
   - **Replay clobbering** — `Backlog::insert` unconditionally replaces an existing entry with a fresh `PendingGeneration` + fresh wall-clock timestamp (`node/src/backlog/mod.rs:266-283`, called from `process_sign_request`, `ops.rs:21`). Nodes restart/replay at different times ⇒ the same stuck request carries wildly different bytes per node, permanently. (The ops.rs:226-233 comment and error #2 independently confirm replay re-inserts phase-1 entries.)
6. **Stuck entries make divergence permanent.** No TTL/expiry exists. Canton's stuck set (18–19 ids, constant across 53 checkpoints and 4 pods in the logs — exactly the error-#1 requestIds) is requeued and re-signed after every catchup (`take_requeueable_requests` → re-sign → `mark_publishing` → publish → `CONTRACT_NOT_FOUND` → entry parked in `PendingPublish` with cohort-local bytes; `execute_publish` retries forever at ≤60s backoff, `node/src/rpc/mod.rs:469-513`). With ≥1 divergent entry at every boundary, no checkpoint ever reaches threshold again.
7. **Frozen NEAR value ⇒ replay-storm + confirmation noise.** The contract's stored checkpoint stays at the last-agreed height (Canton 533730, Ethereum 11243900). Every pipeline select-iteration re-runs `detect_regression` (`pipeline.rs:332-398`), which finds the stale digest matches the *persisted* checkpoint (`find_checkpoint_by_digest` falls through to storage, `mod.rs:657-677`) and re-confirms/re-persists it — the 986×"confirmed and persisted"@533730. Every restart recovers to it and replays the gap (~29k Canton blocks and growing).

Additional log facts: the 53 Canton checkpoints in `canton-checkpoint-logs.json` show only 4 distinct pending-sets (sizes 18/19/20/21 — a constant core with occasional joiners like `2fa493a2` that then never leave: slow accumulation). All 53+20 checkpoint signIds are distinct (heights strictly increase per pod; no cross-incarnation overlap exists in single-node data). Ethereum: pending 376→384 across four checkpoints spanning **18 seconds**, then zero checkpoint creations for the rest of the 5.5h window — the cap filled at 00:42:32 and indexing stalled (defect #1).

## 3. Answer to the dossier's open question

*"Should consensus advance while requests are in-flight, or must the pending set drain first?"* — **Consensus must advance while requests are in-flight.** A busy chain never has an empty or quiescent pending set, so drain-first (fix #2 alone) can never unfreeze Ethereum. The consensus subject must be reduced to what is chain-deterministic: **the set of outstanding request ids at a block height**. Per-node processing phase was never a coherent consensus subject — signing cohorts, `is_proposer`, wall-clock timestamps, and cross-chain observation timing make it unagreeable by construction. Bounded retention (expiry) is *also* needed, but as hygiene, not as the unfreeze mechanism.

## 4. Fix design

### Layer 1 — node-agnostic digest (the unfreeze)

Change `Checkpoint::digest()` (`primitives/src/backlog.rs:65-74`) to hash only chain-deterministic identity, with a version tag for domain separation:

```rust
pub fn digest(&self) -> [u8; 32] {
    let mut hasher = sha3::Sha3_256::new();
    hasher.update(b"ckpt-v2");                       // version/domain tag
    hasher.update(self.chain.caip2_chain_id().as_bytes());
    hasher.update(self.block_height.to_le_bytes());
    for pending in &self.pending_requests {          // already sorted by sign_id
        hasher.update(pending.sign_id.request_id);
        // NOTE: pending.transaction intentionally NOT hashed
    }
    hasher.finalize().into()
}
```

Why request-ids only (alternatives considered and rejected):
- **Canonical status via the dead `digest_bytes()`**: still hashes *phase*, and phase transitions are asynchronous w.r.t. block boundaries (signing-cohort completion, target-chain `ExecutionConfirmed`) — on a 7s-interval chain the divergence windows never close. Also `PublishState::digest_bytes` still embeds `is_proposer`. Rejected; delete the dead code instead.
- **Hashing the request core (args/kind) without status**: `set_request` swaps the whole `IndexedSignRequest` (kind *and* args) when a bidirectional advances to phase 2 (`ops.rs:328-339`), and that flip is triggered by target-chain observation timing — same async divergence. Rejected.
- **Request-ids only**: the set of outstanding ids at height H *is* a deterministic function of chain history, because every set mutation is driven by a source-chain event processed in stream order by the single per-chain consumer (`run_stream`, `node/src/stream/mod.rs:97-116`): inserts by `SignRequest` events, removals by `Respond`/`RespondBidirectional` events, all ≤ H and ordered before `Block(H)`. Replay re-inserts are same-key overwrites (set unchanged). Execution confirmations change an entry's kind/status but never its id. ✓

The `Checkpoint` struct and `PendingTx.transaction` bytes are unchanged — they remain the recovery payload; they just stop being part of the consensus statement. Trust note: a peer-served checkpoint's per-entry state (status/args) is no longer integrity-bound by the digest, only the id set is. Peers are the MPC participant set; poisoned args at worst produce signatures that `PublishAction::new` refuses to publish (liveness, not integrity). Accepted residual risk — document it.

Also in this layer: delete `SignStatus::digest_bytes`/`PublishState::digest_bytes` (dead code that invites phase-hashing back), and invert `test_checkpoint_digest_changes_with_status` into a stability test (see §5).

### Layer 1b — migration (required, or the fix bricks alignment)

The NEAR contract still serves the *old-format* digest (533730 / 11243900). An upgraded node recomputes v2 digests, `find_checkpoint_by_digest` matches nothing, `detect_regression` declares divergence, and `find_consensus_checkpoint` (`node/src/backlog/consensus.rs:126-198`) polls peers forever for a checkpoint whose v2 digest equals the old value — **permanent recovery livelock**. Therefore:

- Add `Checkpoint::digest_legacy()` preserving today's algorithm. Wherever a *consensus* digest is compared against local checkpoints (`find_checkpoint_by_digest`, `detect_regression`, `align_backlog_with_consensus`, and peer validation in `fetch_peer_checkpoint`), match `digest_v2 || digest_legacy`. On legacy match: confirm/persist as today, never regress. Once the first v2 checkpoint lands on NEAR at a higher height (contract accepts any height ≥ existing, `contract/src/lib.rs:854-864`), the legacy path goes dormant; remove it one release later.
- **No contract change needed**: `respond_checkpoint` verifies the threshold signature over `(chain, height, digest)` and stores it — it is agnostic to how the digest was computed. `ConflictingCheckpoint` (same height, different digest) becomes practically unreachable once digests are deterministic.
- Rollout: coordinated deploy. Mixed-version clusters cannot co-sign across versions (old and new digests differ), which merely prolongs the existing freeze until ≥ threshold nodes are upgraded — acceptable on a frozen system; schedule accordingly for mainnet. Immediately after threshold is reached, Canton unfreezes on the first boundary (the stuck ids are chain-derived and provably identical across nodes), consensus jumps 533730→current, and restart replay shrinks from ~29k blocks to ≤ interval.

### Layer 2 — determinism & liveness hardening

1. **Idempotent insert on replay.** `process_sign_request` must not clobber an existing entry (make `Backlog::insert` insert-if-absent, or check-then-skip). Preserves original status/timestamp per the documented contract, kills error #2 at the root, and stops the restart-driven re-sign/re-publish churn that produces error #1 (Fix A stays as defense-in-depth). Chain events are final; a duplicate `SignRequest` for an existing id is always replay.
2. **Reap checkpoint sign tasks.** Record the *checkpoint's* chain (from `SignKind::Checkpoint(cp).chain`) in `task_chains` instead of `request.chain` (NEAR), so `AbortChain` works; additionally supersede: when enqueueing a checkpoint for height h, send `Completion` for that chain's older pending checkpoint sign_ids, and complete tasks whose height ≤ the confirmed consensus height. Ends the zombie-task buildup and proposer-slot contention.
3. **Un-livelock the cap.** Replace stall-on-full with drop-oldest (`BTreeMap::pop_first`) in `Backlog::checkpoint` — checkpoint heights are skippable by design (contract accepts height jumps; `on_consensus_confirmed` already prunes by height). Then remove the `if has_checkpoint_slot` gates from `handle_live`/`handle_catchup` (`pipeline.rs:237,297`) so block/event indexing never halts because consensus is slow. Backpressure, if still wanted, belongs on checkpoint *creation*, never on chain indexing. (Q4 proved this stall is live on all 7 nodes, both chains, today.)
4. **Settlement events must be terminal regardless of entry phase.** `process_respond_bidirectional_event` (`ops.rs:212-248`) refuses to remove an entry whose kind is not `RespondBidirectional` — but replay reconstructs settled entries as phase-1 (`ExecutionConfirmed` comes from the target chain and is never replayed), so an on-ledger settlement can arrive at a phase-1 entry and the request becomes a permanent one-node zombie (production example: `2fa493a2…` on dev-0, §7). On a verified settlement event for a known request_id, remove the entry (and its watchers) whatever its phase. Note the signature check needs care: the settlement signature is over the phase-2 response payload, so `verify_entry_signature` against a phase-1 entry's args will fail — verify event provenance (Canton: signatory/Vault checks already exist in `chain-canton/src/events.rs:145`) rather than signature-vs-entry in this path. This keeps the request-id set replay-deterministic; without it, a restarted node's set diverges until the (post-fix) regression path pulls it back.

### Layer 3 — deterministic expiry of stuck requests (H3 hygiene; product sign-off needed)

Wall-clock TTLs would desynchronize the pending set across nodes and re-freeze consensus. Expiry must be **height-based and chain-derived**: record `origin_block_height` on `IndexedSignRequest` (from the event's block — replay-stable), and when processing `Block(H)`, drop entries (and their execution watchers) with `H − origin > K(chain)` (env-tunable like `CHECKPOINT_INTERVAL_*`; e.g. Canton ~7 days of offsets). All nodes expire the same entry at the same boundary ⇒ set stays agreed. Semantics: an expired bidirectional request whose execution surfaces later hits the already-tolerated "watcher not found" path (`ops.rs:294-302`). For Canton's 18, the on-ledger sign events are consumed — there is nothing left to respond to; expiry is pure cleanup. Alternative considered: emit the `0xdeadbeef` failure-respond on timeout — rejected for now (the target-chain execution may still occur later, and the failure-respond would consume the settlement path); revisit with product.

**Complementary option — offset-anchored ACS reconciliation (surgical fossil drain).** The safe form of "query the chain and remove settled entries": the *indexer* (never the publisher — see principle below), at a checkpoint boundary offset H, queries Canton's ACS with `activeAtOffset = H` for the pending entries' sign-event contract ids and emits synthetic settlement events through the normal stream for those already archived. Anchored at the same offset on every node ⇒ deterministic ⇒ the id-set stays agreed. Drains provably-settled fossils immediately instead of waiting out an expiry window; per-chain work (Canton nearly free; Ethereum needs a "settled as of block H" equivalent). Composes with expiry: reconciliation drains the settled, expiry reaps the abandoned.

**Design principle — the publisher must never mutate the backlog.** Backlog removal is single-writer: only the stream, in ledger order, may remove entries (with settlement verification). The publish path runs on exactly one node (the proposer), so a publisher-side removal shrinks one node's set only ⇒ its next digest diverges from the majority ⇒ regression pulls the majority checkpoint and *resurrects the entry* — the removal cannot even stick. Live-race duplicates need nothing anyway: the consuming exercise lands as a settlement event at an offset every node's stream reads within seconds. Publisher-side dedup stays what Fix A made it: a skip, never a state change.

## 5. Verification plan

- **Unit (mutation-style):** starting from one checkpoint, mutate each formerly-hashed field (status phase, `is_proposer`, `participants`, signature bytes, `unix_timestamp_indexed`) → digest unchanged; add/remove a request id → digest changes. New golden digests. Legacy: `digest_legacy()` reproduces today's goldens.
- **Cross-node simulation:** two `Backlog`s fed the same requests at different wall-times, advanced to different phases (one proposer, one bystander), same height → equal digests and equal checkpoint sign_ids.
- **Integration (the actual bug):** cluster test where a chain has permanently mid-flight/stuck requests across many boundaries → assert the *consensus* checkpoint height keeps advancing (impossible today) and restart replay depth stays ≤ interval.
- **Migration test:** node with old-format persisted checkpoint + old digest stored in the (test) contract → upgraded node aligns via legacy match without entering the regression loop, then signs and stores a v2 checkpoint at a higher height.
- **Layer-2 tests:** replay a `SignRequest` for an advanced entry → status/timestamp preserved; `AbortChain` reaps checkpoint tasks; cap overflow drops oldest and indexing continues.

## 6. Damage summary (why this matters beyond noise)

Frozen consensus ⇒ (a) every restart replays tens of thousands of blocks; (b) replay re-sign/re-publish storms (error #1) with infinite ≤60s-backoff retry tasks per stuck request; (c) unbounded pending accumulation on busy chains; (d) cap-full ⇒ **the node stops indexing the chain entirely** between watchdog cycles — new sign requests and respond events are simply not seen by that node (Ethereum has been in this state most of each pod's life); (e) up to 32 zombie sign tasks per chain contending for 4 proposer slots; (f) **cross-chain coupling — the Ethereum livelock is what mints Canton zombies**: Canton bidirectional deposits complete via `ExecutionConfirmed` observed on Ethereum; with Ethereum indexing dark, phase-2 starves and deposits pile up in phase-1/`PendingExecution` (this is how `2fa493a2` got stuck; it settled only when a restart-replay happened to sweep its execution). The 18 ancients' EVM executions lie *below* Ethereum's frozen checkpoint horizon (11243900), so no replay can ever re-observe them — permanently unsettleable; only expiry/reconciliation (or manual purge) drains them. Post-fix, live Ethereum indexing observes executions within finality and the deposit lifecycle works end-to-end. Open dependency outside this repo: *who broadcasts the bidirectional EVM transaction* (the node is observational) — its reliability bounds how aggressive expiry can be, since an unreliable broadcaster makes `PendingExecution` stalls legitimate flow states rather than bugs.

## 7. Production confirmation (2026-07-16 log pulls — all four discriminators answered)

- **Q1 (cross-node digests), 12h window, 7 nodes (dev-0/3/6/8/9/10/11):** 58 multi-node heights (25 Canton, 33 Ethereum) — **58/58 divergent, zero agreement anywhere**; at every Canton height all 7 nodes produced 7 distinct checkpoint signIds. **Ethereum: the pending request-id SETS are identical across all nodes at all 33 heights** while every digest differs — the content identity agrees perfectly; only the per-node serialized bytes (timestamps/status/publish-state) diverge. This is simultaneously the proof of H1 and the validation of the fix: with the id-set digest, all 33 Ethereum heights would have reached identical digests.
- **Q1 bonus — set divergence manufactured by replay, caught live:** request `2fa493a2…` was held by all 7 nodes up to height 561801; from 561851 six nodes had removed it (its `RespondBidirectionalEvent` settled it) while **dev-0 alone still holds it** — dev-0's entry had been replay-reset to phase-1, so the settlement handler bailed on the kind mismatch (the error-#2 path) and could not remove it. **Error #2 is therefore NOT harmless noise (dossier correction): it is the mechanism that permanently diverges the pending SET itself on whichever node replayed.** With the id-set digest this either self-heals via regression (6/7 agree ≥ threshold → dev-0 regresses to the majority checkpoint and drops the zombie) or is prevented outright by Layer-2 item 4 below.
- **Q2 (freeze start), 30-day retention: EMPTY.** No confirmation at any height other than 533730/11243900 exists in retention — both chains have been frozen for **≥ 30 days**, not days.
- **Q3 (NEAR write path), 14 days: EMPTY.** Zero checkpoint publish attempts, successes, or errors — no checkpoint signature has ever completed. **H2 conclusively dead:** the write path is not failing; it is never reached.
- **Q4 (cap livelock), 48h: 343 watchdog lines, every single one `pendingCheckpoints: 32, hasCheckpointSlot: false`,** context `catchup` (329) / `live block` (14). **All 7 nodes, BOTH chains** — Canton cycling at a median **5.3 min** (= its 315s watchdog exactly), Ethereum at **35.0 min** (= its 2100s watchdog exactly). Reconstructed lifecycle per pod: restart → replay → healthy window while 32 slots burn (Canton ~5.3h at one checkpoint/~10min; **Ethereum only ~4 min** at one/~7s) → cap-full livelock (indexing dead, watchdog churn) → rescued only by the next deploy. **Dev's ~4–6h deploy cadence is masking the severity: with weekly deploys, Ethereum indexing would be down ~100% of the time and Canton >90%.** (Dossier correction: the livelock is not Ethereum-specific — Canton nodes spend the tail of every pod life in it too.)

## 8. Origin (git archaeology) and the in-flight fix branch

- **2026-05-29, PR #830 (`c1d182d4`)** — checkpoints born. The original `checkpoint_digest()` *decoded* each entry and hashed `sign_id + status.digest_bytes()` — canonical bytes, immune to timestamps and raw-CBOR layout (though already phase- and `is_proposer`-sensitive, so divergence-prone under load).
- **2026-06-04 (`cae9bbaa`, "impl Checkpoint::digest")** — **the regression.** `Checkpoint` moved into `mpc-primitives`, but `BacklogEntry` stayed in the node crate, so the decode-based digest couldn't come along; it was replaced by hashing the opaque `pending.transaction` CBOR. Timestamps and full per-node entry state silently entered the consensus hash; `digest_bytes()` became dead code. Layering constraint, not intent.
- **2026-06-19, PR #847 (`f44a3560`)** — the NEAR consensus loop shipped *on top of* the broken digest. The feature is 27 days old as of 2026-07-16; Q2 (empty over 30-day retention) means it only ever agreed in its first days — at empty/quiescent boundaries — and froze as soon as pending sets carried live entries.
- **2026-06-29, PR #919** — `MAX_PENDING_CHECKPOINTS` cap added (the indexing-stall failure mode); **2026-07-08, PR #969** — pipeline watchdog (the Q4 log lines).
- **2026-07-13 (`5e0ceedb`, `origin/xiangyi/fix-checkpoint-digest-consensus`, unmerged)** — Xiangyi Zheng independently authored the Layer-1 core fix: drops `hasher.update(&pending.transaction)` (digest = chain ‖ height ‖ sorted request_ids), inverts the status test, adds ignores-timestamp / differs-for-different-requests tests. **Review verdict: core change correct and matches this design, but MISSING the migration shim (§4 L1b) — deploying it as-is bricks the whole cluster**: every upgraded node fails to match the old-format digest NEAR still serves, enters regression, and loops forever in `find_consensus_checkpoint` (peer digests can never equal the old value). `align_backlog_with_consensus` runs *before* the watchdog-covered phases, so recovery hangs with no escape, no pipeline ever starts, and no node can ever sign a new checkpoint to displace the stale value. Also absent (acceptable as follow-ups): version tag in the preimage, Layer-2 hardening, Layer-3 expiry.
- **Devnet migration shortcut (alternative to the node-side shim):** the contract already ships `#[private] reset_checkpoint(chains)` (`contract/src/lib.rs:1113-1117`) — callable by the contract account to delete the stored checkpoints. Once cleared, the polled watch value becomes `None`, `align_backlog_with_consensus` short-circuits (nothing to align), and fixed nodes proceed. Ordering is forgiving: nodes deployed *before* the reset hang in the peer-poll loop but exit the moment the consensus value empties (`find_consensus_checkpoint` aborts on change/None, `consensus.rs:149-165`). Devnet sequence: deploy Xiangyi's fix → `reset_checkpoint(["Canton","Ethereum"])` → first boundary threshold-signs with matching digests. Keep Redis (nodes replay from 533730 one last time) or wipe it (Canton replays from offset 0; note replay resurrects the ~18 zombies identically on every node — with the id-only digest they're consistent baggage, consensus advances with them inside until expiry/settlement fixes drain them).
