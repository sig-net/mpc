# Midnight API conformance

The reference is [midnight-integration PR #138](https://github.com/sig-net/midnight-integration/pull/138) at **`350f9a3080e4b4073e0f1dafaa3603b05c22be92`**, from which `@sig-net/*` `0.25.0-rc.1` is published and to which the packages are pinned. This matrix covers the MPC's supported Midnight → EVM type-2 → Midnight interface. It does not claim that running the MPC suite runs every test in the upstream repository.

The owning contracts are the pinned [protocol README](https://github.com/sig-net/midnight-integration/blob/350f9a3080e4b4073e0f1dafaa3603b05c22be92/README.md) and [Compact interface](https://github.com/sig-net/midnight-integration/blob/350f9a3080e4b4073e0f1dafaa3603b05c22be92/packages/signet-midnight/src/Signet.compact). Executed outputs follow the Borsh [response serializer](https://github.com/sig-net/midnight-integration/blob/v0.24.0-rc.10/packages/signet-midnight/src/abi-serde.ts) of `@sig-net/midnight` `0.24.0-rc.10` ([midnight-integration PR #58](https://github.com/sig-net/midnight-integration/pull/58)): the Borsh encoding of the output-schema fields in schema order, `bool`, `uint256` (32 bytes, little-endian), `address`, and `bytes1` to `bytes32` only, with the respond schema ignored.

**Configured-cache publication remains an accepted behavioral deviation.** Its tests characterize best-effort publication rather than conformance to the upstream cache guarantee. `Unviable` issuance covers an observed, different watched transaction consuming the same nonce; a consumed nonce without an observed replacement and its inclusion height still remains pending. The rows below distinguish these cases and identify the test layer establishing each property; golden coverage is not described as live-chain coverage.

The request fixture labels its transaction oracle. Eight vectors use the SDK transaction producer and ethers serialization directly. The full-width nonce case uses SDK field assembly plus ethers RLP with the exact integer, because the SDK transaction helper converts the nonce to a JavaScript number and cannot serialize `u64::MAX` safely. That case tests the Compact-declared integer encoding, not support for that value in the SDK's numeric transaction helper.

## Transcript placement and vault flows

The ledger keeps a call in the guaranteed transcript only while its estimated cost fits the guaranteed budget, applies every guaranteed section first, and then applies fallible segments in ascending segment order. The test caller's ballast writes move a call, including the singleton call it makes, to the fallible transcript. The [fixture driver](../chain-signatures/midnight-publisher-ts/devtools/real-stack/fallible.ts) builds each scenario's transaction, checks the partition of every call before submitting it, and checks the ledger outcome afterwards, so a partitioner change fails the test instead of weakening it.

| Requirement | Concrete test evidence | Layer |
| --- | --- | --- |
| A notification from a fallible transcript is indexed, signed, executed, and attested like a guaranteed one when its transaction applies fully | [midnight_stream.rs](../integration-tests/tests/cases/midnight_stream.rs): `midnight_indexes_notifications_by_transcript_placement` submits a wholly fallible call, guaranteed and fallible calls that each notify twice, and a guaranteed intent followed by a fallible intent; [emissions.rs](../chain-signatures/chain-midnight/src/emissions.rs): `captured_applied_fallible_notifications_decode`, `decodes_all_event_kinds_in_either_phase` | Live chain and captured transactions |
| Notifications are indexed in ledger application order: guaranteed notifications first, then fallible segments by ascending segment | Same live test: the mixed transaction, and two fallible intents whose later call has the lower segment, must index in that reversed order; [emissions.rs](../chain-signatures/chain-midnight/src/emissions.rs): `orders_phases_then_segments_and_actions_preserving_native_call_indices` | Live chain and unit |
| A partially successful transaction is not indexed, including the request its guaranteed intent committed | Same live test: a fallible intent fails after its guaranteed intent commits; the driver checks the `FailFallible` status and that only the guaranteed request is in the caller's ledger, and the MPC never indexes or signs either request | Live chain; characterizes the full-success indexing policy below |
| The vault's queued flows complete with the real MPC: deposit, router and wrapper approvals, withdraw, swap, supply, and redeem | `midnight_vault_operations_complete_with_real_mpc` drives the [vendored vault](../chain-signatures/midnight-publisher-ts/devtools/real-stack/erc20-vault.compact), an unmodified copy of [midnight-examples PR #93](https://github.com/sig-net/midnight-examples/pull/93) at `ae4effad7197955eaa9eb175f3eb20939d70febc` built against `@sig-net/midnight` `0.25.0-rc.1`, through [vault.ts](../chain-signatures/midnight-publisher-ts/devtools/real-stack/vault.ts). Each request is started, flushed, sent, attested, queued, flushed again, and completed. Each send's notification comes from the transaction that sent it, in whichever transcript the partitioner placed it; every attestation binds the receipt height and the Borsh output; the vault's queue circuit verifies each attestation from the event alone, its completion circuits check each output against the attested length and hash and settle each request, and the shielded balances match the EVM results | Live chain. The EVM targets are local ERC-20, ERC-4626, and swap-router [mocks](../chain-signatures/contract-eth/contracts/MidnightVaultTargets.sol), so Uniswap and Aave behavior is not covered |

## Run the coverage

Build the pinned Compact caller and vault and the TypeScript publisher, then run the existing library suites and the explicitly ignored seam/live tests:

```sh
just build midnight
cargo test --locked -p mpc-chain-midnight -p mpc-chain-ethereum -p mpc-compact-hashing -p mpc-primitives -p mpc-node
cargo test --locked -p mpc-chain-midnight --features sandbox --lib output_storage::tests
just test-midnight-seam
just test-midnight
```

`just test-midnight` also builds the Solidity targets and runs the three live tests in `cases::midnight_stream`; `just test-midnight <test>` runs one of them. Each starts fresh local Midnight, Ethereum, and MPC services. `midnight_to_ethereum_to_midnight_consumes_caller_response` includes both conformance assertions and the explicitly labeled cache-deviation characterization above. The live tests do not establish the configured-cache guarantee or historical replacement detection. On systems with short Unix socket path limits, give the TypeScript driver a short process-scoped `TMPDIR`.
