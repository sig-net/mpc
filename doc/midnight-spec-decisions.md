# Signet on Midnight (SGN2) — decision log & rejected alternatives

Companion to [`midnight-spec.md`](./midnight-spec.md). The spec states **what to build**; this file records **why**, **what was rejected**, **how the design evolved**, and **the platform facts each decision rests on**. When a spec section removed a long rationale, it points here. Keep this append-only in spirit: when a decision is superseded, record the supersession rather than deleting the old reasoning.

---

## A. Version evolution

**SGN1 — event-chunking transport (`mpc/doc/signet-midnight-events.md`, built).** Requests and responses rode MIP-0002 contract events (`Misc { name, payload }`), 5-part chunked reassembly, a ~4-word calldata cap, and Jubjub Schnorr attestations (ledger 8 had no in-circuit ECDSA). Discovery depended on the Midnight GraphQL indexer's `contractEvents` subscription. Superseded because events are non-consensus, capped at 256 B, have no inclusion-proof path, and are served only by a prerelease indexer.

**SGN2 draft v2 — storage-transport with a smart hub (`midnight-erc20-vault`: `signet-hub`/`signet-reference`, as-built and deploy-proven on ledger 9).** Requests moved into the caller's own ledger; a `signet-hub` singleton did discovery + **in-circuit ECDSA attestation verification** (`postRespondBidirectional` verified `secp256k1EcdsaVerify` against a stored `mpcAttestationKey`), **payment intake** (`payAndNotifyUnshielded` / `payAndNotify` + `feePaid`/`feeCoins`), **fee sweeps** (`sweepFeesUnshielded`/`sweepFeesShielded`, MPC-signature-gated, `sweepNonce`-replay-protected), and **notify-log GC** on respond. The request id was `persistentHash([pad(32,"signet:midnight:request:v2"), sender, persistentHash(record)])` (domain-tagged, nested). The attestation digest was hash-attested SHA-256 (`SHA-256(rid ‖ SHA-256(output))`) because rc.0-era Compact had no in-circuit keccak.

**SGN2 draft v3 — dumb append-only store (current; `sig-net/midnight-integration`).** PR #24 review (Bernard / Felipe) ruled the central contract must be a **dumb event store**: it holds no keys, verifies nothing, takes no payment, sweeps nothing, deletes nothing. This removed, from v2: hub-side ECDSA verification and `mpcAttestationKey` (§B.1), payment intake + sweeps (§B.2, → §8 payment TODO), notify-log GC (§B.3), the domain-tagged/nested request id (§B.4 → flat parity hash), and the hash-attested digest (§B.5 → keccak parity, now possible because verification moved to the integrator's claim circuit where keccak/zkir-v3 is available). The platform facts verified during the v2 build (anchored reads, state layout, encoding stability, prover status) carried forward unchanged (§G).

**Revision log (v3):**
- 2026-07-20 — initial v3 draft from the PR #24 rulings.
- 2026-07-21 — `requestNonce` → caller-supplied salt (§B.6); rid-preimage parity settled (§F); notification structs aligned to the post-review PR shapes (§H); discovery source settled as the node-only block-walk composition, indexer non-normative (§B.7); §5.4 rewritten as the explicit proof path; publisher trust-plane / transport / deployment recorded (§D, §B.8); the "own node mandatory" framing corrected to threshold independence (§C.1).

## B. Rejected alternatives (with reasoning)

**B.1 — Hub-side (central-contract) signature verification.** *Rejected (v3, PR #24).* The v2 hub verified the MPC attestation in-circuit before storing it. Ruling: the central contract verifies nothing — it stores whatever args it was called with; consumers verify (off-chain for raw signatures, in the integrator's claim circuit for attestations), exactly as the EVM `ChainSignatures` contract does ("an event bus... performs no signature verification itself"). This also removes `mpcAttestationKey` from the contract (integrators pin the expected key themselves) and lets the contract compile to v2 ZKIR (no `secp256k1EcdsaVerify`), which unblocks the live MPC path on the current prover. A spam/garbage post is harmless: it lands under a fresh count key and is filtered by the consumer's verification.

**B.2 — Payment intake + fee sweeps in the hub.** *Rejected for V1 (PR #24); deferred to a separate contract.* v2 had CCC-callable `payAndNotifyUnshielded`, shielded `payAndNotify`, `feePaid`/`feeCoins`, and two MPC-signature-gated sweep circuits. Removed because a frozen contract can't safely carry evolving payment policy, and egress (withdraw) has no `msg.sender`/`kernel.caller()` to authenticate an admin. Payment returns as a *separate* contract beside the dumb store (or via a maintenance-authority circuit addition, P7). Intake feasibility is settled (P3, §G.5): a CCC callee CAN take unshielded payment (proven live end-to-end); shielded intake cannot ride a CCC (callees have no Zswap local state). See §8 of the spec.

**B.3 — Notify-log GC on respond.** *Rejected (v3).* v2 removed a request's `notifyLog` entry when its response was posted, to bound map growth. Ruling: nothing is ever removed — all stores grow monotonically. Rationale: a `postRespond`-side GC is permissionless/unverified, so a griefer could delete a paid-but-unserviced request's evidence; and append-only state is what makes the state-read catch-up lossless (spec §5.1). The O(entries) request-path insert cost is an operational parameter to monitor, not a protocol bound.

**B.4 — Domain-tagged / nested request id.** *Rejected (v3, PR #24).* v2's `persistentHash([pad(32,"signet:midnight:request:v2"), sender, persistentHash(record)])` deviated from the cross-chain shape with a domain tag and an inner hash. Ruling (Pessina, PR #24): "we don't use it on other chains." v3 is one flat `SHA-256(sender ‖ record-bytes)` — the EVM/Solana shape (sender first, flat, no tag). Full parity analysis: §F.

**B.5 — Hash-attested attestation digest.** *Superseded (v3).* v2 signed `SHA-256(rid ‖ SHA-256(output))` because rc.0-era Compact had no in-circuit keccak and no variable-length in-circuit hashing, and because the *hub* verified it (fixed work for any output size). Since v3 moves verification to the integrator's claim circuit — which knows its output size `Bytes<K>` at compile time and can use zkir-v3 keccak — the digest is now the full cross-chain-parity `keccak256(rid ‖ serializedOutput)`. Gated on probe P11 (in-circuit keccak over `rid ‖ Bytes<K>`).

**B.6 — `requestNonce` as a contract `Counter` read.** *Rejected (2026-07-21).* Reading a `Counter`'s value into the stored record pins that value in the transcript; transcript replay validates recorded reads, so two users of one caller contract reading the same counter in one block would invalidate one transaction (concurrency conflict). `Counter.increment` itself is a commutative, conflict-free delta — the problem is the *read*. Replaced by a caller-supplied salt (dapp picks a counter value or random bytes) + the `!member(rid)` insert guard. Safety is unaffected: the rid also binds the prover's witness-derived `commitment`, so no salt choice lets one user mint another's rid; a same-user duplicate is the same request and the guard rejects it.

**B.7 — Indexer as the discovery foundation.** *Rejected as the normative source (2026-07-21); kept as a non-normative optional source.* The Midnight indexer's `contractActions(address, offset)` subscription is genuinely address-scoped with existing-then-live replay (verified, §G.4) — the closest thing to "subscribe to my contract." Rejected as the foundation because (a) every rung of the proof path (spec §5.4) verifies data the node block-walk already holds, whereas an indexer must be bypassed for every proof; (b) an indexer stream's *completeness* — the property that matters for discovery liveness — is exactly what no proof can cover, while the block-walk's completeness is auditable block by block; (c) it re-introduces the service+DB dependency SGN2 deliberately dropped, and no released indexer follows a ledger-9 chain. It may serve as an optional *second* source behind the same seam once a released ledger-9 indexer ships and the CCC-ride-along-indexing check passes (does a nested hub call index under the hub's address?). It must never be the only discovery source.

**B.7b — `state_subscribeStorage` as the primary wake-up.** *Deferred.* The node's key-scoped `state_subscribeStorage(keys)` + historical `state_queryStorage(keys, from, to)` are the node-native approximation of "subscribe to our contract," and replayable — but they key on *raw storage keys*, and whether the central contract's state maps to its own key(s) or shares one ledger-wide blob is the open P1-proper question (`midnight_contractState` abstracts it; `childstate_*` + `state_getChildReadProof` suggest per-contract child tries). If the mapping is per-contract, this can replace body-filtering as the wake-up while the block walk stays for provenance/proofs. Probe alongside P1-proper.

**B.8 — `Command::new` child process for the publisher.** *Rejected in favor of a sidecar container.* Both eliminate the network attack surface (the real win is "no listening socket," not "subprocess"). A `Command::new` child runs inside the node's container/cgroup, so a proving OOM (respond proving is memory-heavy) or a toolkit RCE via a malicious block byte can take down or reach the keyholding node. A separate **sidecar container** gives its own cgroup/filesystem boundary — a proving OOM or RCE is isolated to the sidecar. Note: `Command::new` is *not* the repo's "redis pattern" (redis is a co-located sibling on a localhost port, not a child of mpc-node); the faithful redis analog is the localhost-bound sidecar. The only real as-built security finding is the SGN1 publisher's `0.0.0.0` bind with no auth while holding the funding wallet — an unauthenticated gas-drain + OOM-DoS surface; the fix is binding `127.0.0.1` / in-pod only (a unix socket or shared-secret header is optional belt-and-suspenders).

**B.9 — Docker-in-the-loop publisher (default `docker` intent mode).** *Rejected for production.* The SGN1 publisher's default `generate-intent` step runs `docker run <toolkit-image>` per respond, needing a Docker socket from the node's environment (a privilege concern) and with no repo precedent for runtime `docker run`. Production uses **native intent mode**: bundle the native toolkit binary + Node/toolkit-js + compactc + prover keys into the publisher's own image, no docker-in-docker at serve time.

**B.10 — No generic signer singleton (ever, under current Compact).** *Standing rejection.* Interface circuits can't be generic (CoIP-2); callees can't run witnesses (identity binding must live in the caller's proven circuit); callees have no Zswap state; and a shared circuit's compile-time capacity caps force worst-case proving cost on everyone. Capacities stay per-integrator generics.

**B.11 — Two-pass "MPC signs a request hash, client submits to a central store."** *Rejected (design discussion, v2 era).* Would centralize storage standards in one contract but costs an extra MPC pass + Midnight finality + two ZK proofs (~minutes of added latency), still needs notify-or-whitelist, and is hard to explain to integrators. Revisit only if single-contract storage becomes a hard requirement.

**B.12 — Binding the storage ordinal into the request id.** *Rejected.* Would make an untrusted notification self-validating, but is unnecessary given the no-op guards (a wrong-ordinal read fails the rid recompute or resolves to an inert no-op; destination-chain nonce + first-write semantics) and would forbid relocating the request map after requests exist. Position stays a discovery hint carried in the notification, never a security input.

**B.13 — Path string in the record.** *Rejected (v3, PR #24).* Carrying the derivation path as a `Bytes<256>` hex string forces the in-circuit hex-decode-and-assert machinery (`assertPathCommitment`/`assertHexOf`/`charToNibble`: 64 per-nibble assertions) because Compact can hex-*decode* but not hex-*encode* in-circuit. The record instead stores the 32-byte `commitment` raw and the MPC derives `path = lowercase-hex(commitment)`. Semantically identical, far cheaper. Contract-owned literal paths (a vault's `"vault"` treasury path) need no user binding and can arrive later as a record variant.

## C. Corrections made in review

**C.1 — "Operator-owned node is a mandatory security floor" → corrected to threshold independence (2026-07-21).** An earlier draft framed the own node as a Midnight-unique mandatory security floor pre-proofs. That was overstated. Verified against the code: the Ethereum RPC is operator config (`MPC_ETH_EXECUTION_RPC_HTTP_URL`, third-party-able); requests reach cluster agreement (`backlog/consensus.rs`); and Ethereum ships an optional Helios light client (`--eth-light-client`, "use Helios light client instead of direct RPC"). So the Midnight RPC is architecturally identical to any chain's RPC. The base security model across all chains is **threshold independence** (a single lying RPC can't forge a signature — it must appear in a threshold of independently-chosen views), and Midnight's proof ladder is the direct analog of Helios (an enhancement that trust-minimizes the RPC, making a *third-party* endpoint more acceptable over time). Own-node today is an availability necessity (no public ledger-9 RPC exists yet), not a security mandate. The one real hygiene rule (general, not Midnight-specific): don't collapse threshold independence by pointing the whole signing threshold at one shared endpoint. Full model: §E.

## D. Publisher trust plane (mechanism, never authority) — full reasoning

The `midnight-publisher` and the in-workspace `chain-midnight` crate are the **same trust level** — our code, our deploy, the operator's host. There is no "trusted vs untrusted" hierarchy between them; retire that framing. The architectural split is by **attack surface**, not provenance:

- The publisher carries a huge parser surface (the whole polkadot/ledger dependency tree) and ingests attacker-authored on-chain bytes — a permissionless chain is an honest *conduit* for adversarial data. So a crafted on-chain record could, in principle, trip a memory-safety bug in that dependency tree.
- Therefore every **security decision** — the rid recompute today, proof verification tomorrow — lives in the small `chain-midnight` crate over **raw bytes**, never in the publisher.
- **Consequence:** an ordinary publisher decode *bug* produces bytes that fail the rid recompute → a dropped request (liveness), never a wrong signature (safety).
- **Honest V1 limit:** with no proofs, a *fully compromised* publisher (RCE) is as dangerous as a compromised node — it controls everything it returns, including the "raw" bytes, so it could fabricate a self-consistent `(record, rid, sender)` triple. The mechanism-not-authority rule contains *bugs*, not *RCE*, while there are no proofs. (And both are still bounded by threshold independence, §E — a single compromised publisher serving one node can't reach a signing threshold.)
- **The payoff is the proof path.** Read proofs (rung 3) verify the raw record bytes against the header `state_root` *before* the recompute — so a compromised publisher can no longer forge. Keeping the decision co-located with proof verification is exactly what lets rungs 2–4 demote **both** the node and the publisher out of the trusted set together. Make the publisher an authority instead and its decode is trusted forever — no proof could reach it.

Mental model: a **decision plane** (small, safety-critical — recompute + proof-check) and a **mechanism plane** (the publisher — decode/prove/submit, large surface, output always re-checked downstream). Same trust level today; the split is what lets that trust shrink as proofs land.

## E. RPC trust model (full reasoning)

Capability is not the constraint — everything the discovery pipeline needs at every proof rung is the Midnight node's standard public RPC surface (141 methods enumerated on 2026-07-21: subscriptions, `chain_*`, `midnight_contractState`, `state_getReadProof`, `grandpa_proveFinality`; no sidecar, no custom build; the required set is Substrate's safe-RPC class — the one unsafe-class method in the design, ranged `state_queryStorage`, belongs to the non-normative alternative only). The constraint is trust, and it mirrors every other chain:

- **Base model (all chains): trust-your-RPC, protected by threshold independence.** A request is signed only after cluster consensus (`backlog/consensus.rs`) and a signing threshold, so it must appear in a *threshold* of independently-chosen RPC views. A fabricated request (a victim's public commitment inside an attacker-authored record) is not actually on-chain, so honest nodes reading their own RPCs never see it; and storage-location=sender + the commitment binding defeat any *real* on-chain forgery attempt regardless. So a third-party Midnight RPC is as acceptable as a third-party eth RPC. Hygiene rule: don't point the whole threshold at one shared endpoint (a single compromised provider is then a correlated failure across the threshold).
- **Trust-minimization is an enhancement, and Midnight is well-positioned for it.** Ethereum offers an optional Helios light client (`--eth-light-client`). Midnight's proof ladder (spec §5.4) is the direct analog: read/inclusion proofs let each operator *verify* its RPC's answers against header roots; finality proofs verify the headers themselves. Proofs make a *third-party* Midnight RPC progressively **more** acceptable — the opposite of an own-node mandate. Until finality proofs land, a malicious endpoint can still serve a self-consistent fake chain to the one operator trusting it, but that operator is one vote in the threshold, so the systemic bar stays "corrupt a threshold of endpoints."
- **Why self-run today anyway — availability, not security.** No public ledger-9 RPC exists yet, so an own/local node is the only *available* option until the roll-forward. Whoever serves it must be a *capable* endpoint (finalized bodies `archive-canonical`, the subscription + `state_getReadProof` methods, accepts submissions). Hosted endpoints bring rate-limit / ws-stability constraints that per-block body fetching would stress — so even post-roll-forward an own/dedicated node may be pragmatic, but that is an ops call, not a security floor.

## F. Request-id parity (full analysis)

Byte-exact cross-chain equality does not exist even among the current chains — EVM `sign` uses `abi.encode` (32-byte slots) while EVM `signBidirectional` uses `abi.encodePacked`, and Solana packs the sender as its base58 *string* where EVM packs 20 raw address bytes. No consumer ever compares ids across chains (ids live per source chain); the invariant every chain shares is the **shape**, and Midnight matches it element-for-element:

| element | EVM sign | EVM signBidirectional | Solana | Midnight |
|---|---|---|---|---|
| hash | keccak256 | keccak256 | keccak256 | SHA-256 — forced: id computed in-circuit as the caller's map key; keccak is v3-gated and needless there |
| encoding | `abi.encode` | `abi.encodePacked` | `abi_encode_packed` | canonical Compact struct bytes (fixed-width, LE ints) — forced: no dynamic types |
| sender | 20-byte address, first | 20-byte address, first | pubkey base58 string, first | 32-byte contract address, first |
| tx/payload | `payload` bytes32 | `serializedTransaction` raw | `transaction_data` raw | decomposed `EVMType2TxParams` — forced: caller circuits enforce fields |
| routing fields | path, keyVersion, chainid, algo, dest, params | caip2, keyVersion, path, algo, dest, params | caip2, keyVersion, path, algo, dest, params | same set, same order (commitment for path; source chainid implicit) |
| extras | — | — | — | requestNonce (forced: map-keyed storage) + schemas (whole-stored-record superset) |
| domain tag / nesting | none | none | none | none |

The Midnight preimage binds the record's stored serialization, a strict **superset** of the EVM preimage (adds `requestNonce` + the two schemas). Binding more is harmless and keeps one canonical byte layout for both storage and hashing.

## G. Verified platform facts (provenance)

Facts the design rests on, with how/when verified. Re-verify against release tags as the rc line moves.

**G.1 — Anchored contract-state reads (P1, live, 2026-07-18).** `midnight_contractState(contract_address, at?)` accepts and *honors* an optional finalized-block-hash `at` (positional + named); proven not silently-latest — a bogus hash errors, and a contract absent at genesis correctly reports contract-not-present. Address must be raw 64-hex (no `0x`). `state_getReadProof` is exposed and functional (`{at, proof:[trie nodes]}`), plus `state_getChildReadProof` and `midnight_ledgerStateRoot(at?)`. Open: mapping a contract's state to raw Substrate storage key(s) (P1-proper).

**G.2 — Node RPC surface (2026-07-21).** All 141 methods enumerated on `midnight-node:2.0.0-rc.3`. No tx-by-address subscription; subscriptions are chain heads (`chain_subscribeFinalizedHeads`, `chainHead_v1_follow`), `state_subscribeStorage`, runtime version, GRANDPA/BEEFY justifications, own-tx watch. `grandpa_proveFinality` / `grandpa_subscribeJustifications` and `sidechain_getEpochCommittee` are exposed (rung-4 material). The `midnight_*` namespace is read-only queries.

**G.3 — Node pruning defaults (2026-07-21, read from the node binary `--help`).** `--blocks-pruning` defaults to `archive-canonical` ("keep only the data of finalized blocks" — every finalized body retained indefinitely). `--state-pruning` defaults to 256 blocks (limits historical state reads, not bodies). Sync mode defaults to `full` (not warp). So a default operator node supports arbitrary-depth block-walk catch-up; ops rules: never `--blocks-pruning <NUMBER>`, never warp-sync; `--state-pruning archive` only for historical execution proofs.

**G.4 — Indexer `contractActions` (2026-07-21, extracted from the ledger-9-prerelease indexer binary `4.4.0-pre-alpha…l91r3-n2r3`).** GraphQL `subscription { contractActions(address, offset) }` — "subscribe to contract actions with the given address starting at the given offset or at the latest block if the offset is omitted"; stream is existing-then-live (replays from the offset, then live). Endpoint `/graphql/ws`, `graphql-transport-ws`, per-session subscription quotas. It is `contractActions` (deploy/call/update — fires on calls) that fits SGN2, NOT `contractEvents` (MIP-0002 events only — our contracts emit none). No *released* indexer follows a ledger-9 chain yet.

**G.5 — CCC unshielded payment (P3, live e2e, v2 era).** A CCC callee CAN take unshielded payment (`receiveUnshielded` is a pure kernel-effects op; wallet balancing funds the callee's claim; ledger balance verification sums per-call effects with no root/sub distinction) — proven end-to-end on the live l9 stack (one tx: integrator → CCC → hub credited exactly the fee). Shielded intake in a callee is impossible (Zswap ops throw — callees have no Zswap local state; the tx model derives shielded offers from the root call only). Bears on the payment TODO (§B.2).

**G.6 — Encoding stability (Midnight, Edward, 2026-07-13).** A deployed contract's state encoding is frozen at its compile version; field-position addressing holds for its lifetime; new-compiler encoding changes affect only newly compiled contracts (absorbed reader-side via the notification `version`); whole-ledger migrations are network-wide and non-silent (structured-forks process). Not obtained: an explicit promise that release notes always flag encoding changes — mitigated by the §5.2 CI watch on release *tags*. The rc line already moved ledger state encoding v17→v18 and changed `Field`'s hash representation mid-line.

**G.7 — Prover status (2026-07-18).** No released prover — HTTP proof server or the pinned `midnight-node-toolkit` native prover — proves zkir-v3 circuit *calls* (`proving.rs:94` rejects `ir-source[v3-generic]`); deploys prove, calls do not. Under v3 this gate no longer touches the central contract (v2 ZKIR) or the MPC respond path — only integrator claim circuits (zkir-v3 keccak + `secp256k1EcdsaVerify`) remain upstream-gated until a v3-capable prover ships.

**G.8 — State layout (P8, simulator dumps, v2 era).** ≤15 fields = flat top-level array; ≥16 bucket into ≤15-wide child arrays (observed 16→1+15, 27→12+15; last bucket holds 15, partition compiler-internal). A struct map value = one cell, one atom per field in declaration order; `Bytes<N>`/`Uint` atoms trailing-zero-trimmed. A Compact `List<T>` = recursive cons node `[headValue, tailList, lengthCounter]` (simulator-dump-verified, corrected a hand-derived flat model).

**G.9 — Toolchain floors.** Cross-contract calls ≥ 0.32.105. In-circuit `secp256k1EcdsaVerify` behind `--feature-zkir-v3`; the big-endian msgHash convention + `secp256k1EcdsaRecover` removal shipped at 0.33.0-rc.1; the successive-verify optimizer crash (#609) and curve-point/foreign-scalar hash alignment (#608) fixed at 0.33.0-rc.2 — so integrator claim circuits floor at 0.33.0-rc.2. Since 0.33.0-rc.1, `Bytes<32>`→secp256k1-scalar casts reduce mod the modulus (never reject out-of-range) and are little-endian while `msgHash` is big-endian.

## H. PR #24 relation (notification structs)

This spec encodes where the PR #24 review thread settled, not the snapshot's current bytes. The snapshot's `SignBidirectionalNotification { version, payload: Bytes<65> }` carried the rid *inside* the payload and landed in a rid-keyed upsert map. The review changed all three:
- payload `Bytes<65>` → `Bytes<128>` (Felipe: headroom for future versions);
- the rid moves out of the payload into the key (Felipe: it's duplicated — the rid is already the map key);
- entries become **count-keyed** so nothing can overwrite (Felipe: "they should not be able to overwrite a valid request"; Bernard: counter into the key).

The spec additionally generalizes the envelope to both request kinds via the `txParamType` byte — the snapshot implements bidirectional only, and plain `sign` parity is in scope. Other PR #24 rulings folded into the design: drop the hub attestation key / pk-in-response (§B.1); remove `evmAddressAbiValue` (calldata words are verbatim bytes; helpers live in the SDK); sender must be hashed into the rid but *not* domain-tagged (§B.4); the `mpcPubKeyHash` sealed ledger is unnecessary (integrators pin their own expected key); payment is a documented TODO with a ticket, not a V1 feature (§B.2).
